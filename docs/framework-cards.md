# Карточки кандидатов: методологические рамки (семинар 02)

Распределение анализа:

| Участник | Карточки |

### Карточка: OWASP SAMM 2 *(анализ участника 2)*

- **Название и версия:** OWASP Software Assurance Maturity Model, SAMM 2.
- **Для чего предназначена:** модель развития практик безопасности ПО в
  организации — оценить текущее состояние, задать целевой уровень зрелости и
  построить программу улучшений.
- **Почему подходит нашему проекту:** даёт структуру практик (Governance,
  Design, Implementation, Verification, Operations) и критерии уровней; полезна
  как язык для описания текущего состояния.
- **Что придётся адаптировать:** почти всё — модель описывает организацию и её
  программу развития, а не один учебный выпуск; оценка зрелости для пары на
  семь недель не строится.
- **Что не покрывает:** конкретные технические требования к приёму файлов,
  критерии готовности конкретного выпуска.
- **Доступна ли нужная версия:** да, бесплатно на owasp.org.
- **Предварительное решение:** не выбираем как основную (командная оценка
  зрелости не проводится); отдельные идеи (например, метрики §10) можно
  позаимствовать без смены рамки.

### Карточка: ISO/IEC 27034-1:2011 *(анализ участника 2)*

- **Название и версия:** ISO/IEC 27034-1:2011 «Information technology —
  Security techniques — Application security — Part 1: Overview and concepts».
- **Для чего предназначена:** понятийная и процессная рамка безопасности
  приложений в организационном контексте: роли, отнесение безопасности
  приложений к управлению организацией.
- **Почему подходит нашему проекту:** помогает структурировать понятия
  (контекст приложения, роли, процессы), что полезно для §4.
- **Что придётся адаптировать:** значительно — рамка организационного уровня;
  для двух студентов почти каждое положение требует упрощения в несколько раз.
- **Что не покрывает:** конкретных требований к web-приложению и проверок;
  сама по себе не отвечает, что делать на этой неделе.
- **Доступна ли нужная версия:** ограниченно — стандарт ISO платный, у команды
  есть только пересказы и аннотации; это отдельный аргумент против выбора
  (требование 6 из шага 1).
- **Предварительное решение:** не выбираем — слишком общая, недоступна
  полная версия, требует непропорциональной адаптации.

### Карточка: NIST SP 800-218 SSDF 1.1 *(общая, участник 2)*

- **Название и версия:** NIST Secure Software Development Framework (SSDF),
  SP 800-218, версия 1.1 (февраль 2022).
- **Для чего предназначена:** набор практик безопасной разработки, которые
  интегрируются в существующий жизненный цикл: подготовка организации (PO),
  защита ПО (PS), создание безопасного ПО (PW), реагирование на уязвимости (RV).
- **Почему подходит нашему проекту:** компактна (четыре группы практик), каждая
  практика формулируется как требование с результатом (task), что прямо
  переводится в действия одного из двух участников; покрывает полный цикл
  включая реагирование после выпуска — что нужно для §4 и §10.
- **Что придётся адаптировать:** роли и «организацию» заменяем двумя
  участниками с правилом «ведущий + проверяющий»; не все практики берём —
  только девять применимых положений (см. таблицу в §2).
- **Что не покрывает:** технические требования к приёму и хранению файлов —
  закрываются дополнительным источником (ASVS V5).
- **Доступна ли нужная версия:** да, бесплатно на csrc.nist.gov (PDF и
  страница практик).
- **Предварительное решение:** основная рамка.

### Карточка: OWASP ASVS 5.0.0

- **Для чего предназначена:** каталог требований и способов проверки для
  web-приложений; удобна для выборки требований под конкретную область.
- **Почему подходит:** даёт конкретику по загрузке файлов (V5.1–V5.3), которой
  нет в SSDF.
- **Что не покрывает:** не является рамкой жизненного цикла — не заменяет
  SSDF как основу.
- **Доступна ли версия:** да, бесплатно на owasp.org.
- **Предварительное решение:** дополнительный источник, только глава V5.

### Карточка: ГОСТ Р 56939-2024

- **Для чего предназначен:** требования к процессам безопасной разработки в
  российской нормативной базе; ориентирован на организацию-разработчика и
  подтверждение соответствия.
- **Почему не подходит как основа:** команде не нужно подтверждение
  соответствия; большинство процессов (управление, документация, метрики
  организации) для двух человек неприменимы без диссонирующей адаптации.
- **Версия:** действующий, текст доступен (Интерстандарт, платно; обзоры —
  открыто).
- **Предварительное решение:** не выбираем. Отмечаем как кандидата, если бы
  проект требовал российской нормативной базы.

### Карточка: IEC 62443-4-1:2018

- **Для чего предназначен:** требования к безопасному жизненному циклу
  продуктов промышленной автоматизации и систем управления.
- **Почему не подходит:** продукт — обычный web-сервис, а не ICS/embedded;
  требования (управление уязвимостями продукта на десятилетия, safety-контекст)
  избыточны.
- **Версия:** доступна обзорно; полный текст платный.
- **Предварительное решение:** не выбираем — несоответствие типу продукта.
